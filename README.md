# homelab-terraform

Provisions a Talos Linux Kubernetes cluster on Proxmox and bootstraps it with ArgoCD. After the initial apply, ArgoCD manages all further workloads from the [homelab](../homelab) mono repo.

## What Terraform does

```
tofu apply
  ├── Downloads Talos ISO to Proxmox
  ├── Creates control plane and worker VMs
  ├── Generates cluster secrets (talos_machine_secrets)
  ├── Renders per-node machine configs from your variables
  ├── Applies machine configs to all nodes
  ├── Bootstraps etcd
  ├── Retrieves kubeconfig and talosconfig
  ├── Uploads an SSH deploy key to your GitHub mono repo
  ├── Clones the mono repo into .homelab-apps-checkout/
  ├── Installs ArgoCD (upstream argo-cd chart)
  ├── Installs the homelab-bootstrap Helm chart (apps/ in the mono repo)
  │     ├── ArgoCD repo credential Secret (SSH deploy key)
  │     ├── AppProject
  │     └── ApplicationSet → ArgoCD discovers and deploys everything else
  └── Creates the tailscale-operator OAuth Secret (if configured)
```

This project uses [OpenTofu](https://opentofu.org/) (`tofu`), not Terraform — same HCL and workflow, different binary.

## Repo structure

```
main.tf                     All resources: ISO, VMs, Talos bootstrap, ArgoCD
variables.tf                Input variables with descriptions
outputs.tf                  VM MAC addresses, kubeconfig/talosconfig paths
providers.tf                Provider configuration
versions.tf                 Provider version constraints
terraform.tfvars.example    Copy to terraform.tfvars and fill in
.sops.yaml                  age public keys that secrets.enc.yaml is encrypted to
secrets.enc.yaml            sops-encrypted secrets (Proxmox token, Tailscale OAuth, Cloudflare token)
secrets.example.yaml        Template showing which keys secrets.enc.yaml holds
modules/
  proxmox_vm/               Creates one Proxmox VM from a Talos ISO
scripts/
  tofu.sh                   Runs tofu with secrets.enc.yaml decrypted into its environment
  fritzbox-reserve-ips.sh   Optional, standalone: create FRITZ!Box DHCP reservations from a MAC → IP file
.homelab-apps-checkout/     Gitignored — mono repo, re-cloned on every apply
```

## Secrets and state

| File | In git? | Contains |
|---|---|---|
| `secrets.enc.yaml` | ✅ encrypted | Proxmox token, Tailscale OAuth client, Cloudflare API token — encrypted with [sops](https://github.com/getsops/sops) + [age](https://github.com/FiloSottile/age) |
| `~/.config/sops/age/keys.txt` | ❌ never | Your age private key — the one thing to back up (password manager) and copy to a new machine |
| `terraform.tfvars` | ❌ never | Node IPs and other environment-specific, non-secret values |
| `terraform.tfstate` | ❌ never | Terraform state — contains cluster CA/bootstrap secrets (`talos_machine_secrets`), the Proxmox token, the ArgoCD SSH deploy key, and the Tailscale OAuth client |
| `kubeconfig` | ❌ never | Cluster access credentials — regenerated by Terraform |
| `talosconfig` | ❌ never | Talos client config — regenerated by Terraform |

# Deployment guide

Start here if you have a bare Proxmox machine and nothing else.

## Prerequisites

### Tools — install on the machine running OpenTofu

```bash
brew install opentofu talosctl kubectl gh sops age
```

| Tool | Purpose |
|---|---|
| `tofu` | Provision VMs and orchestrate the bootstrap (talks to the Talos API directly via the `siderolabs/talos` provider and installs Helm charts via the `helm` provider — no separate CLIs needed for that) |
| `talosctl` | Optional — talk to Talos nodes directly for manual debugging (health checks, logs) |
| `kubectl` | Interact with the Kubernetes API |
| `gh` | Provides the `GITHUB_TOKEN` used to upload the deploy key and clone the mono repo |
| `sops` + `age` | Encrypt/decrypt `secrets.enc.yaml` |

### Proxmox

A Proxmox VE host reachable on your LAN with an API token. Create one:

1. Log in to Proxmox → **Datacenter → Permissions → API Tokens → Add**
2. User: `root@pam`, Token ID: `terraform`, uncheck "Privilege Separation"
3. Copy the token secret — shown only once
4. Grant the token the `Administrator` role at the `/` (Datacenter) level

Verify the API is reachable:
```bash
curl -sk https://<proxmox-ip>:8006/api2/json/version | jq .data.version
```

### GitHub

A GitHub account with:
- The [homelab](../homelab) mono repo pushed and accessible
- The `gh` CLI logged in with `repo` scope:

```bash
gh auth login
gh auth status   # confirm 'repo' scope is listed
# If missing: gh auth refresh -s repo
```

### Tailscale

A Tailscale account. The Tailscale **Kubernetes operator** (deployed by ArgoCD from the mono repo) exposes cluster services on your tailnet — the nodes themselves do not join Tailscale.

You need an **OAuth client** for the operator:
1. Go to [Tailscale admin → Settings → OAuth](https://login.tailscale.com/admin/settings/oauth)
2. Create a client with **Devices: write** scope, tagged `tag:k8s`
3. Copy the client ID and secret into `secrets.enc.yaml` (Step 1)

### Cloudflare

A Cloudflare account managing your domain's DNS. You need an API token with:
- `Zone:DNS:Edit`
- `Zone:Zone:Read`

scoped to your domain's zone. Create it at **Cloudflare dashboard → My Profile → API Tokens**.

Terraform itself doesn't use this token: cert-manager reads it from OpenBao, where you write it in Step 6. Store it in `secrets.enc.yaml` (Step 1) so it's available on any machine.

## Step 1 — Secrets and terraform.tfvars

### Secrets: secrets.enc.yaml

Secrets live in `secrets.enc.yaml`, encrypted with sops to the age public keys listed in `.sops.yaml`. The file is committed, so a fresh clone has every secret. All you need on a new machine is your age private key.

**First time ever: create an age key** (skip if `~/.config/sops/age/keys.txt` already exists):

```bash
mkdir -p ~/.config/sops/age
age-keygen -o ~/.config/sops/age/keys.txt   # prints your public key
```

Back up `keys.txt` in your password manager. If you lose it, you can't decrypt `secrets.enc.yaml`. Put the printed public key (`age1...`) in `.sops.yaml`.

**Create the encrypted secrets file**, using `secrets.example.yaml` as the template for which keys to add:

```bash
sops secrets.enc.yaml   # opens $EDITOR, encrypts on save
git add secrets.enc.yaml && git commit -m "Add encrypted secrets"
```

| Key | What to put |
|---|---|
| `TF_VAR_proxmox_api_token` | Token from the Proxmox prerequisite, in format `root@pam!terraform=<secret>` |
| `TF_VAR_tailscale_oauth_client_id` / `TF_VAR_tailscale_oauth_client_secret` | OAuth client from the Tailscale prerequisite (or empty to skip) |
| `CLOUDFLARE_API_TOKEN` | Token from the Cloudflare prerequisite — used in Step 6 |

To change a secret later, run `sops secrets.enc.yaml` again. To read one, run `sops -d --extract '["CLOUDFLARE_API_TOKEN"]' secrets.enc.yaml`.

**On a new machine:** restore `~/.config/sops/age/keys.txt` from your password manager (or `export SOPS_AGE_KEY=AGE-SECRET-KEY-...`) and clone the repo. Nothing else is needed.

To let another machine or person decrypt with their own key, add their public key to `.sops.yaml` and run `sops updatekeys secrets.enc.yaml`.

**Running tofu:** always go through `./scripts/tofu.sh` instead of `tofu` directly. It decrypts `secrets.enc.yaml` into the tofu process's environment (via `sops exec-env`, so plaintext never touches disk) and sets `GITHUB_TOKEN` from `gh auth token`. Every `TF_VAR_*` key becomes the matching Terraform variable.

> Don't also set the secret variables in `terraform.tfvars`. Values in tfvars take precedence over `TF_VAR_*` environment variables, so they'd silently override the encrypted ones.

### Non-secret values: terraform.tfvars

```bash
cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars
```

Fill in every value. Key things to set:

| Variable | What to put |
|---|---|
| `proxmox_endpoint` | `https://<proxmox-ip>:8006` |
| `proxmox_node` | Node name shown in the Proxmox sidebar (usually `pve`) |
| `proxmox_datastore_id` | Storage pool for VM disks — run `pvesm status` on the host |
| `proxmox_iso_datastore_id` | Storage pool for ISO files |
| `talos_schematic_id` | Leave as default (qemu-guest-agent only) unless you need extra extensions |
| `control_plane_nodes` | Name, IP, and VM ID for each control plane node |
| `worker_nodes` | Name, IP, and VM ID for each worker node |
| `node_network_gateway` | Your LAN gateway IP |
| `network_bridge` | Proxmox network bridge (check **Node → System → Network**, usually `vmbr0`) |
| `argocd_github_repo` | `yourname/homelab` |

## Step 2 — Create VMs and get MAC addresses

```bash
tofu init
./scripts/tofu.sh apply -target=module.control_plane_vms -target=module.worker_vms
```

Once done, get the MAC addresses:

```bash
tofu output control_plane_mac_addresses
tofu output worker_mac_addresses
```

Go to your router and create a **DHCP reservation** for each MAC → IP pair matching what you set in `terraform.tfvars`. The IPs must match exactly — Talos machine configs are generated with those IPs baked in.

### FRITZ!Box: create the reservations with a script

On a FRITZ!Box, `scripts/fritzbox-reserve-ips.sh` creates the reservations from a plain MAC → IP file. It's standalone: Terraform doesn't run it. It uses [`fritz_lease.py`](https://github.com/jvejmelka/fritzbox-static-lease), downloaded at a pinned, checksummed commit into a gitignored virtualenv in `.fritzbox-static-lease/`.

FRITZ!Box's official API (TR-064) can't set reservations, so this relies on the box's **undocumented** internal API. It's tested upstream on FRITZ!OS 8.25 only, and a FRITZ!OS update can break it. If it fails, set the reservations by hand in the UI.

One-time setup: in the FRITZ!Box UI, create a dedicated user under **System → FRITZ!Box Users** with the **FRITZ!Box Settings** permission. Turn off the extra confirmation (button press/phone) for that user, or writes are silently discarded.

The VMs must have booted at least once first: the FRITZ!Box can only pin devices it has seen on the network.

```bash
cp scripts/fritzbox-reservations.txt.example scripts/fritzbox-reservations.txt
$EDITOR scripts/fritzbox-reservations.txt   # MACs from the outputs above, IPs from terraform.tfvars

export FRITZ_USER=terraform                  # the user created above
./scripts/fritzbox-reserve-ips.sh            # prompts for the password
```

### Reboot the VMs onto their reserved IPs

The VMs keep their current DHCP lease until they restart. Reboot them all via the Proxmox API:

```bash
./scripts/tofu.sh apply -var reboot_vms=true -target=terraform_data.vm_reboot
```

The next plain `./scripts/tofu.sh apply` shows these `terraform_data.vm_reboot` entries being destroyed. That's expected and does nothing to the VMs.

## Step 3 — Boot the VMs into Talos maintenance mode

The VMs start automatically when they're created. Open the console on one in the Proxmox web UI — you should see the Talos boot screen within a minute. Talos waits in **maintenance mode** until it receives a machine config.

Wait until all nodes are reachable before continuing:

```bash
# Talos maintenance API port
nc -zv 192.168.1.110 50000
```

---

## Step 4 — Full apply

```bash
./scripts/tofu.sh apply
```

Terraform will, in order:

1. Generate cluster secrets (`talos_machine_secrets`) — stored only in `terraform.tfstate`
2. Render per-node machine configs from your variables
3. Apply machine configs to all nodes (they reboot and configure themselves)
4. Bootstrap etcd on the first control plane node
5. Retrieve `kubeconfig` and `talosconfig`
6. Upload the SSH deploy key and clone the mono repo into `.homelab-apps-checkout/`
7. Install ArgoCD from the upstream `argo-cd` chart
8. Install the `homelab-bootstrap` Helm chart (`apps/` in the mono repo) which deploys:
   - The ArgoCD repo credential Secret (SSH deploy key)
   - The `homelab` AppProject
   - The `infrastructure` ApplicationSet
9. Create the `operator-oauth` Secret in the `tailscale` namespace (if `tailscale_oauth_client_id` is set)

ArgoCD immediately begins syncing the mono repo and deploying infrastructure in phase order.

This takes **10–15 minutes** end to end.

## Step 5 — Approve the Tailscale operator devices

If you set `tailscale_oauth_client_id`/`tailscale_oauth_client_secret`, Terraform already created the `operator-oauth` Secret in Step 4 — skip straight to approving the devices below.

If you left them empty, apply the secret manually instead:

```bash
export KUBECONFIG=$(pwd)/kubeconfig

kubectl create namespace tailscale --dry-run=client -o yaml | kubectl apply -f -

kubectl apply -f - <<EOF
apiVersion: v1
kind: Secret
metadata:
  name: operator-oauth
  namespace: tailscale
stringData:
  client_id: "YOUR_CLIENT_ID"
  client_secret: "YOUR_CLIENT_SECRET"
EOF
```

Once the secret exists, the operator registers the Envoy Gateway and Teleport as tailnet devices. Approve them in the [Tailscale admin console](https://login.tailscale.com/admin/machines).

## Step 6 — Unseal OpenBao and configure secrets

OpenBao starts sealed on first deploy. Port-forward to it and initialise:

```bash
kubectl port-forward -n openbao svc/openbao 8200 &
export BAO_ADDR=http://localhost:8200

# Initialise — prints 5 unseal keys and a root token
# Store these somewhere safe (password manager)
bao operator init

# Unseal — run 3 times, each time with a different key from the output above
bao operator unseal

# Enable Kubernetes auth so External Secrets Operator can read secrets
bao auth enable kubernetes
bao write auth/kubernetes/config \
  kubernetes_host="https://kubernetes.default.svc"

# Create a policy that allows reading any secret
bao policy write external-secrets - <<EOF
path "secret/data/*" { capabilities = ["read"] }
EOF

# Create a role bound to the ESO service account
bao write auth/kubernetes/role/external-secrets \
  bound_service_account_names=external-secrets \
  bound_service_account_namespaces=external-secrets \
  policies=external-secrets \
  ttl=1h

# Write the Cloudflare API token (from secrets.enc.yaml) so cert-manager can do DNS-01 challenges
bao kv put secret/cert-manager/cloudflare \
  api-token="$(sops -d --extract '["CLOUDFLARE_API_TOKEN"]' secrets.enc.yaml)"
```

Once the Cloudflare token is written, `cert-manager-config` syncs successfully and the Envoy Gateway gets its Let's Encrypt certificate.

---

## Step 7 — Create the first Teleport user

```bash
kubectl exec -n teleport deploy/teleport -- \
  tctl users add admin --roles=editor,access --logins=root
```

Follow the printed URL to set a password. Then log in from your local machine:

```bash
# Connect to Teleport via its Tailscale hostname
tsh login --proxy=teleport:443 --user=admin

# Register the cluster with kubectl
tsh kube login homelab

# Verify
kubectl get nodes
```

From this point on, use `tsh` and `kubectl` through Teleport for all cluster access. The local `kubeconfig` is only needed for recovery.

## Accessing the cluster during bootstrap

Before Teleport is running you can use the local kubeconfig:

```bash
export KUBECONFIG=$(pwd)/kubeconfig
kubectl get nodes
```

To check ArgoCD sync status during bootstrap:

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443 --kubeconfig kubeconfig
# Open https://localhost:8080
# Password:
kubectl get secret argocd-initial-admin-secret -n argocd \
  --kubeconfig kubeconfig \
  -o jsonpath="{.data.password}" | base64 -d
```

For Talos node debugging:

```bash
export TALOSCONFIG=$(pwd)/talosconfig
talosctl --nodes 192.168.1.110 health
talosctl --nodes 192.168.1.110 logs kubelet
```
